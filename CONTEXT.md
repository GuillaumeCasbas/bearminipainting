# MiniPaint Project Context

This file contains the **validated decisions** and **technical context** for the MiniPaint project (Warhammer army painting tracker).
It should be used by all agents/sessions to maintain consistency.

---

## 🎯 Project Goal
Create a **front-end only** (MVP) application to **organize and track painting tasks** for Warhammer armies.
- **Tech Stack**: React + Zustand (state management) + TypeScript + Jest (TDD).
- **Persistence**: `localStorage` (nested structure: projects contain units).
- **Architecture**: Hexagonal (Clean Architecture) with **Core + Adapters + Ports**.

---

## 📦 Core Domain (Entities)

### **Project**
- **Fields**:
  - `id`: UUID (string, generated by frontend).
  - `name`: string (required).
  - `code`: string (required, **globally unique**).
  - `units`: `Unit[]` (default: `[]`).
- **Methods**:
  - `getCompletionRate(): number`:
    - Returns `100` if `units.length === 0`.
    - Otherwise: `(totalDoneTodos / totalTodos) * 100` (rounded to nearest integer).

### **Unit**
- **Fields**:
  - `id`: UUID (string, generated by frontend).
  - `name`: string (required).
  - `code`: string (required, **unique within its project**; the full code `project.code-unit.code` is unique globally).
  - `projectId`: string (required, references a `Project`).
  - `todos`: `Todo[]` (6 default todos auto-created).
- **Methods**:
  - `getCompletionRate(): number`:
    - Returns `100` if `todos.length === 0`.
    - Otherwise: `(doneTodos / totalTodos) * 100` (rounded to nearest integer).
- **Default Todos**:
  Automatically added on instantiation:
  | Label         | Order | Status   |
  |---------------|-------|----------|
  | "Assembly"    | 10    | TODO     |
  | "Primer"      | 20    | TODO     |
  | "Basecoat"    | 30    | TODO     |
  | "Effects"     | 40    | TODO     |
  | "Base"        | 50    | TODO     |
  | "Varnish"     | 60    | TODO     |

### **Todo**
- **Fields**:
  - `id`: UUID (string, generated by frontend).
  - `label`: string.
  - `status`: `TodoStatus` (enum: `TODO` or `DONE`).
  - `order`: number (see ordering rules below).
- **Ordering Rules**:
  - Default todos: fixed orders (10, 20, 30...).
  - Custom todos: added **at the end** (`order = lastOrder + 10`) for MVP.
  - Future: Reordering via dedicated use case (e.g., `ReorderTodosUseCase`).

## 🔌 Ports (Interfaces)
Located in `core/ports/`.

⚠️ **Note**: These interfaces are provided as **examples**. **Do not implement all methods exactly as shown** — each feature should add only what is necessary, following the **YAGNI** principle ("You Aren't Gonna Need It").

### **ProjectRepository**
```typescript
interface ProjectRepository {
  save(project: Project): Promise<void>;
  findAll(): Promise<Project[]>;
  findById(id: string): Promise<Project | null>;
  findByCode(code: string): Promise<Project | null>;
  delete(id: string): Promise<void>;
}
```

### **UnitRepository**
```typescript
interface UnitRepository {
  create(unit: Unit): Promise<void>;
  update(unit: Unit): Promise<void>;
  findById(id: string): Promise<Unit | null>;
  findByCode(code: string): Promise<Unit | null>;
  findByProjectId(projectId: string): Promise<Unit[]>;
  delete(id: string): Promise<void>;
}
```

> **Note**: The `save()` method has been refactored into `create()` and `update()` for explicit separation of concerns (BEA-23).

## 🎯 Use Cases (MVP)
Located in `core/usecases/`.

| Use Case                     | Inputs               | Output       | Rules                                                                                     |
|------------------------------|----------------------|--------------|-------------------------------------------------------------------------------------------|
| `CreateProjectUseCase`       | `name`, `code`        | `Project`    | Throws error if `code` is not unique (checked via `ProjectRepository.findByCode`).        |
| `CreateUnitUseCase`          | `name`, `code`, `projectId` | `Unit`  | Throws error if `code` is not unique **within the project** **OR** `projectId` does not exist.                  |
| `AddTodoToUnitUseCase`       | `unitId`, `label`     | `Unit`       | Adds todo **at the end** (`order = lastOrder + 10`).                                         |
| `ToggleTodoStatusUseCase`    | `unitId`, `todoId`    | `Unit`       | Toggles `TODO` ↔ `DONE` for the specified todo.                                          |

## 🏗️ Architecture
```
src/
├── core/                          # Domain Layer (100% framework-agnostic)
│   ├── entities/                 # Business entities (Project, Unit, Todo)
│   ├── ports/                    # Interfaces (ProjectRepository, UnitRepository)
│   └── usecases/                 # Business logic (use cases)
│
├── adapters/                     # Infrastructure Layer
│   ├── persistence/              # Data access (e.g., localStorage)
│   │   ├── localstorage/         # LocalStorage implementations
│   │   │   ├── project.repository.ts  # Implements ProjectRepository
│   │   │   └── unit.repository.ts   # Implements UnitRepository
│   └── ui/                       # UI-specific adapters (e.g., React hooks)
│
└── ui/                           # UI Layer (React + Zustand)
    ├── stores/                   # Zustand stores
    │   └── useProjectStore.ts     # Manages state, calls use cases via adapters
    └── components/               # React components
        ├── ProjectForm/
        ├── ProjectList/
        ├── ProjectDetail/
        ├── UnitDetail/
        └── Toast/                  # Toast notifications (extension of base architecture)
```

> **Note**: The architecture diagram above serves as a **base structure**. It is possible to add elements (like `Toast/`) to develop the project beyond the initial scope.

## 💾 Persistence (localStorage)
- **Structure**: Nested (projects contain units).
  ```json
  {
    "projects": [
      {
        "id": "1",
        "name": "Space Marines",
        "code": "NMS",
        "units": [
          {
            "id": "1",
            "name": "Intercessor",
            "code": "IA-01",
            "projectId": "1",
            "todos": [...]
          }
        ]
      }
    ]
  }
  ```
- **Note**: Despite nested structure, **two separate repositories** (`ProjectRepository` + `UnitRepository`) are used for cleaner architecture and future backend migration.
- **Desynchronization Risk**: If a `Project` is deleted, its `Unit` entries must be manually deleted (handled in use cases).

---

## 🧪 Testing Strategy (TDD)
- **Core Layer**: 100% TDD (Jest).
  - Write tests **before** implementing entities/usecases.
  - Mock repositories in tests (manual mocks, no external libraries).
- **UI Layer**: Tests for React components (optional for MVP).

## 📌 Important Notes
1. **Full Unit Code**: Computed **on-the-fly** in UI/Store as `${project.code}-${unit.code}`.
   - Not stored in `Unit` entity to avoid coupling.
2. **Language**: All code and error messages **must be in English**.
